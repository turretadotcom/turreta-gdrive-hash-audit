# Google Drive to Local File Matcher

`match_gdrive_to_local.py` matches files listed in a Google Drive inventory CSV against possible original files stored on a local disk.

It is designed to work with the CSV output generated by:

https://github.com/turretadotcom/turreta-gdrive-hash-audit

The main use case is when files in Google Drive have been resized or transcoded before upload and therefore no longer have the same checksum as the original local file.

For example:

```text
Google Drive: IMG_4802-rs.jpg
Local disk:   IMG_4802.jpg
```

Because resizing changes the file contents, the Google Drive MD5/SHA checksums will not match the original local file. This tool instead finds possible matches by filename and then calculates fresh hashes for the local candidate files.

## What it does

The script:

1. Reads a `gdrive_hashes.csv` file generated by `turreta-gdrive-hash-audit`.
2. Recursively scans a local directory.
3. Removes the configured resize suffix, `-rs` by default, from filenames before comparison.
4. Finds possible local matches based on the normalized filename stem.
5. Supports cases where video transcoding also changed the extension.
6. Calculates MD5, SHA-1, and SHA-256 for matched local files.
7. Writes the Google Drive metadata and local-file metadata into a new CSV.
8. Preserves multiple possible matches instead of silently choosing one.
9. Does not modify any Google Drive or local files.

## Requirements

- Python 3.10 or newer recommended
- Standard Python library only
- A CSV inventory generated by `turreta-gdrive-hash-audit`

No Google API credentials are required by this script because it works only with the exported CSV.

## Input CSV

The expected input is the CSV created by:

```bash
python -m gdrive_hash_audit.main
```

By default that project creates:

```text
gdrive_hashes.csv
```

The expected columns are:

```text
path
name
id
mimeType
size
md5Checksum
sha1Checksum
sha256Checksum
createdTime
modifiedTime
```

Example:

```csv
path,name,id,mimeType,size,md5Checksum,sha1Checksum,sha256Checksum,createdTime,modifiedTime
Photos/IMG_4802-rs.jpg,IMG_4802-rs.jpg,1ABC...,image/jpeg,512345,abc...,def...,123...,2026-01-01T10:00:00.000Z,2026-01-01T10:00:00.000Z
```

The script validates the header before starting. If required columns are missing, it exits with an error instead of producing an incomplete result.

## Matching logic

### Resized images

A Google Drive filename such as:

```text
IMG_4802-rs.jpg
```

is normalized to the stem:

```text
img_4802
```

A local file such as:

```text
IMG_4802.jpg
```

is normalized to the same stem:

```text
img_4802
```

The files are therefore treated as possible matches.

### Case-insensitive matching

Filename matching is case-insensitive.

These are treated as the same normalized stem:

```text
IMG_4802-rs.JPG
img_4802.jpg
Img_4802.JPG
```

### Video extension changes

The script does not require extensions to match by default.

This is intentional because a resize or transcode process may change the file format:

```text
Google Drive: family-video-rs.mp4
Local disk:   family-video.mpg
```

Both normalize to:

```text
family-video
```

The result will indicate that the extension changed.

If you want extensions to match exactly, use:

```text
--strict-extension
```

### Multiple possible matches

If several local files have the same normalized stem, all of them are written to the result.

For example:

```text
/photos/old/IMG_4802.jpg
/photos/imported/IMG_4802.jpg
/backup/IMG_4802.png
```

If they all qualify as candidates, the output contains one row for each candidate.

This is intentional. The tool is designed to identify possible relationships rather than guess which file is definitely the original.

## Basic usage

Assume this layout:

```text
project/
├── gdrive_hashes.csv
└── match_gdrive_to_local.py
```

and your local files are stored under:

```text
/media/karl/BACKUP
```

Run:

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP
```

The default output is:

```text
gdrive_local_matches.csv
```

## Specify input and output files

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP \
    --input gdrive_hashes.csv \
    --output gdrive_local_matches.csv
```

Short forms are also supported:

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP \
    -i gdrive_hashes.csv \
    -o gdrive_local_matches.csv
```

## Process only resized files

If you only want Drive files whose filename contains the resize suffix immediately before the extension:

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP \
    --only-rs
```

For example, this would process:

```text
IMG_4802-rs.jpg
holiday-rs.mp4
document-rs.pdf
```

while ordinary files without `-rs` would be skipped.

## Include unmatched Google Drive files

By default, only matched Drive rows are written.

To also write Drive files for which no local candidate was found:

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP \
    --include-unmatched
```

This is recommended when you are using the result as part of a larger file-audit workflow.

Unmatched rows will contain:

```text
match_status = unmatched
candidate_count = 0
```

and the local-file fields will be empty.

## Require the same extension

By default:

```text
movie-rs.mp4
```

can match:

```text
movie.mpg
```

because the stem is the same.

To require extensions to match:

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP \
    --strict-extension
```

With this option:

```text
movie-rs.mp4 -> movie.mp4
```

can match, while:

```text
movie-rs.mp4 -> movie.mpg
```

will not.

For the initial discovery of resized or transcoded files, it is usually better to leave strict-extension mode disabled.

## Use another resize suffix

The default resize suffix is:

```text
-rs
```

You can override it:

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP \
    --suffix "-small"
```

Then:

```text
IMG_4802-small.jpg
```

would be compared against files such as:

```text
IMG_4802.jpg
```

## Recommended command

For a first full comparison:

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP \
    --input gdrive_hashes.csv \
    --output gdrive_local_matches.csv \
    --include-unmatched
```

If you specifically want to investigate resized Google Drive files:

```bash
python3 match_gdrive_to_local.py /media/karl/BACKUP \
    --input gdrive_hashes.csv \
    --output resized_local_matches.csv \
    --only-rs \
    --include-unmatched
```

## Output CSV

The output preserves all columns from the original Google Drive inventory.

These original fields remain available:

```text
path
name
id
mimeType
size
md5Checksum
sha1Checksum
sha256Checksum
createdTime
modifiedTime
```

The script then adds:

```text
normalized_stem
drive_extension
drive_has_resize_suffix
match_status
match_type
same_extension
candidate_count
local_path
local_name
local_extension
local_size
local_mtime_ns
local_md5
local_sha1
local_sha256
hash_error
```

## Output field descriptions

### `normalized_stem`

The filename stem used for matching after removing the resize suffix.

Example:

```text
IMG_4802-rs.jpg
```

becomes:

```text
img_4802
```

### `drive_extension`

The extension of the Google Drive file.

Examples:

```text
.jpg
.mp4
.pdf
```

### `drive_has_resize_suffix`

Indicates whether the Google Drive filename had the configured suffix.

Example:

```text
IMG_4802-rs.jpg
```

results in:

```text
True
```

### `match_status`

Possible values:

```text
matched
unmatched
```

Unmatched rows are only written when `--include-unmatched` is used.

### `match_type`

Describes why the local file was considered a candidate.

Possible values include:

```text
exact_filename
resized_name_same_extension
resized_name_extension_changed
local_has_rs_same_extension
local_has_rs_extension_changed
same_stem_same_extension
same_stem_extension_changed
```

### `same_extension`

Indicates whether the Google Drive file and local candidate use the same extension.

Example:

```text
IMG_4802-rs.jpg -> IMG_4802.jpg
```

results in:

```text
True
```

while:

```text
movie-rs.mp4 -> movie.mpg
```

results in:

```text
False
```

### `candidate_count`

The number of local files found with the same normalized stem.

A value greater than `1` means the match is ambiguous and should be reviewed.

### `local_path`

Absolute path to the matched local candidate.

Example:

```text
/media/karl/BACKUP/Photos/2024/IMG_4802.jpg
```

### `local_name`

Filename of the local candidate.

### `local_extension`

Extension of the local candidate.

### `local_size`

Local candidate size in bytes.

### `local_mtime_ns`

Local filesystem modification time represented in nanoseconds.

This value is useful for later integration with file-audit manifests.

### `local_md5`

MD5 checksum calculated from the local candidate.

### `local_sha1`

SHA-1 checksum calculated from the local candidate.

### `local_sha256`

SHA-256 checksum calculated from the local candidate.

### `hash_error`

Contains the filesystem or permission error if a local candidate could not be read.

Normally this field is empty.

## Important checksum behavior

A resized or transcoded file should not be expected to have the same hash as its original.

For example:

```text
Local original:
IMG_4802.jpg
MD5 = AAAA...

Google Drive resized copy:
IMG_4802-rs.jpg
MD5 = BBBB...
```

Different hashes do not mean the files are unrelated.

They mean the binary contents are different.

The purpose of this script is to establish a possible relationship using the filename and then record the local original's hashes for future processing.

## Why calculate all three local hashes?

The tool calculates:

```text
MD5
SHA-1
SHA-256
```

in a single read of the local file.

This allows the resulting inventory to be used with different audit tools later.

For long-term integrity checking, SHA-256 is the preferred checksum.

MD5 remains useful because Google Drive commonly exposes an MD5 checksum for uploaded binary files.

## Performance

The script first indexes local filenames without hashing every file.

Only files that become possible candidates are hashed.

This avoids reading the full contents of unrelated local files.

If several Google Drive rows refer to the same local candidate, the local hash is cached for the current run so the file is not unnecessarily hashed again.

Large video files can still take time because the entire candidate file must be read to calculate checksums.

## Safety

The script is read-only with respect to your files.

It does not:

```text
rename files
move files
delete files
resize files
modify metadata
upload files
download files from Google Drive
```

It only:

```text
reads the Google Drive CSV
scans local filenames
reads candidate local files for hashing
writes a new CSV report
```

## Suggested workflow

A useful backup workflow is:

```text
Google Drive
     |
     | turreta-gdrive-hash-audit
     v
gdrive_hashes.csv
     |
     | match_gdrive_to_local.py
     v
gdrive_local_matches.csv
     |
     v
review / reconcile / process local originals
```

For files without `-rs`, matching hashes can later provide strong evidence that the Drive copy and local file are byte-for-byte identical.

For `-rs` files, the filename relationship can be used to associate the resized Drive copy with the original local file while keeping separate hashes for both versions.

## Example

Google Drive inventory contains:

```text
path: Photos/2024/IMG_4802-rs.jpg
name: IMG_4802-rs.jpg
md5Checksum: 012345...
sha256Checksum: abcdef...
```

The local disk contains:

```text
/media/karl/BACKUP/DCIM/IMG_4802.jpg
```

The generated comparison row may contain:

```text
normalized_stem: img_4802
match_status: matched
match_type: resized_name_same_extension
candidate_count: 1

local_name: IMG_4802.jpg
local_path: /media/karl/BACKUP/DCIM/IMG_4802.jpg
local_md5: ...
local_sha1: ...
local_sha256: ...
```

The Google Drive hashes remain in the same row, so both the resized Drive version and original local version can be tracked together.
